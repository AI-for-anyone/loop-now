# Loop Now

Updated: 2026-11-16. This is the repository's only main project document; it keeps only the current overview, the key conventions, and the items that still need to be confirmed.

## What the project is

A general-purpose multi-Agent collaboration platform that runs locally. People configure projects, Agents, accounts and Skills in the web console and talk to the Manager, which arranges the tasks. Model integration, code review, QA and production troubleshooting are carried by project Prompts, Skills and workflows. It is positioned as a workbench for one person leading a team of Agents; plugins let the team's capabilities grow without the platform's authors being involved, and are the source of the project's vitality as an open-source project.

The project's source code is licensed under Apache-2.0; see `LICENSE` in the repository root. Third-party code and fonts keep their original licenses. The repository is at `AI-for-anyone/loop-now` (transferred from `hust2018` to this organization and made public on 2026-10-28; the remote keeps only the main branch, and the first tag is v0.1.0; all three repositories have secret scanning and push protection turned on), the official plugin market index repository is `AI-for-anyone/loop-now-market`, and the first market plugin is `AI-for-anyone/loop-now-plugin-slack`.

## Modules and code

| Module | Current capabilities | Entry points |
|---|---|---|
| Console | Project/Agent configuration, chat, Inbox, task canvas, streaming node conversations and artifacts, run logs | `web/src/` |
| Server | Go HTTP service, identities and permissions, configuration, task scheduling, SSE, persistence | `internal/server/`, `cmd/loop-server/` |
| Executor | One local process manager plus two runtime drivers: the bundled Pi (RPC) and the Claude Code on the user's own machine (stream-json); separate workspaces/sessions, installation of CLIs at pinned versions, shallow clones | `internal/server/executor/local/` (`pirpc/`, `ccstream/`), `internal/server/claudecli/` |

| Accounts and tools | Project-shared model/CLI accounts; Codex, GitHub, Google and Lark user authentication; connection verification, scanning and importing local configuration; gh, lark-cli, gcloud, psql, mysql | `internal/server/cliauth/`, `modelauth/`, `clitemplate/`, `cliimport/`, `cliverify/` |
| Plugin system | Second version: Pi extensions + a shared Node host, four kinds of Hook, manifest first, official webhook/hello/playwright | `plugins/` (SPEC, host, sdk, official), `internal/server/plugins/`, `internal/server/pluginhost/`, `internal/pluginmanifest/`, `web/src/features/plugins/` |

The APIs are defined in `api/openapi.yaml` and `api/agent-openapi.yaml`; the database migrations are in `internal/server/store/migrations/`. `auth-helper/` and `scripts/lark-user-variant/` provide helper components for authentication and for running.

## Key conventions

- The hierarchy is Organization → Project → Agent, plus platform Agents; organization management is not open yet. People configure permissions; the Manager can only choose among Agents that are already configured and cannot grant permissions on the fly.
- The project Prompt is automatically layered onto every Agent in the project, and the project's rules win when there is a conflict; a convention written in a Prompt is not the same as a permission check enforced by the program.
- A regular Agent keeps its own workspace and session; inside a task an independent copy is used, and it is reused continuously for the same task and the same Agent. When a task ends, its execution resources are reclaimed, and the records, the session archive and the artifacts are kept.
- Regular configuration takes effect from the next dispatched message. Once a task has started, its workflow, configuration, permissions and account versions are fixed; an ordinary retry does not refresh credentials. Linear flows, conditions and bounded loops are supported; parallel branches that join are not supported for now.
- The Inbox queues by default, and interrupting can be chosen instead; after an interrupt, work continues according to the new message. Chat on a task node goes through the Inbox as well. Multiple runs of the same node are shown one after another with the boundaries marked, and the draft is kept while reading history.
- sleep is an idle wait and can be woken early by a queued message. In each turn the Agent decides for itself whether to wait again; after the end node submits and ends its turn, the platform completes the task automatically.
- The project stores model and CLI accounts in one place, and Agents draw on them according to permissions and selection rules; database tools can have multiple accounts configured. The personal edition has no master key: credentials are stored in plaintext in the SQLite database in the data directory, so the data directory and the backups need to be protected; model credentials are provided through execution-scoped files.
- Explicitly switching the Lark user account for a blocked task is supported: the two members (the one who submits for testing and the one who follows up on results) and the target version are fixed, the original results/session are kept, and only a new QA continuation is arranged. Account login succeeded, switch succeeded, QA sent and QA passed are different outcomes.
- Write actions use a stable actionId; when a result is unclear, look up the original action first, and do not create another action to guess or send again.
- The console is loopback-only on this machine and has no login; Agents use process tokens; external identities get access through a separate TLS port and an explicit allowlist. It is currently a single instance on one machine, and the limits of isolation under the same system user are accepted.

## Current design direction

- The console's English interface is done (2026-10-30, PR #2, #7, #6, #8, #16, #19): all interface copy is collected into two tables of the same shape, `web/src/i18n/zh-CN/` and `en-US/` (the types are derived from zh-CN, a key missing from en-US is a type error, and there is a "no Chinese in the English table" check); the language is decided in this order: `?lang=`, the choice saved in this browser, then the browser's language, and global settings has a language card; English headings use Bricolage Grotesque; the test environment is pinned to zh-CN, and there are separate en-US rendering tests area by area; free text from the server (error messages and the like) is mapped by error code in English mode and shown as is when no mapping is found, and `FieldError` has no error codes yet. Accompanying changes (PR #18): on a fresh install the default organization and project names are now `default` (environment variables can still override them, and existing databases are not touched); the fakePi used in tests gained a neutral-reply mode, `FAKEPI_NEUTRAL=1`; the README and the docs home page switched to English screenshots, and the number of official plugins was changed to three.
- Repository process (decided by the user on 2026-10-30): main is protected, everyone can merge only through a PR, and the three CI checks must pass (at present the branch is also required to be up to date with the latest main, so merges are serial); internal work opens PRs stage by stage, and test fixes are saved up into batches; after a PR is merged, the branch and the worktree are deleted immediately. The timing flakiness on GitHub Actions has been fixed at the root in the cliauth, conversation, httpapi, pluginhost and cliimport tests and in the Web shell, chat and import tests (PR #1, #10, #14, #20). PR #21 from the external contributor airob0t (all-in-one Compose, Linux arm64 CLI templates, an editable Pi models.json plus migration 034) has been reviewed and changes were requested; 034 was applied on 2026-10-31 together with `loop-now-page-scroll-20261031-1`.
- Storage uses SQLite only (decided by the user on 2026-11-02, to pave the way for desktop distribution; the code is on branch `sqlite`, aligned with how PocketBase does it): the PostgreSQL and Redis runtime dependencies are removed. The driver is modernc.org/sqlite (pinned to v1.60.1, SQLite 3.53.4, pinned as a pair with the libc version); in the data directory `LOOP_NOW_DATA_DIR` (default `~/.loop_now`, with the databases under `db/`), `data.db` holds the 84 business tables (including outbox-style ones such as plugin_events and deliveries) and `events.db` holds the four log tables (kept for 90 days), all STRICT; the read pool is concurrent, the write pool is a single connection, every write transaction uses BEGIN IMMEDIATE, and the PRAGMAs follow PocketBase; there is no consistent snapshot across the two databases, so business decisions must not read across files (the `stop_requested` column removed the only place that did). Row locks, advisory locks and pg_notify are all removed; plugin events are recorded into plugin_changes by capture triggers on five tables, and Go generates them in one place before commit and wakes the host after commit (compared one by one against the 38 events of the old PG triggers and found identical); now(), clock_timestamp() and iso_time() are registered in the driver, so the SQL is written as before. Redis's locks, event streams and in-flight replies are now in-process, queuing lives only in the database, and an instance lock file guarantees that there is only one server for a given data directory; a normal shutdown writes in-flight replies to disk, and they are lost on a crash (accepted by the user). Maintenance: a PASSIVE checkpoint every 5 minutes; daily TRUNCATE, optimize, log cleanup and a `VACUUM INTO` backup (`LOOP_NOW_BACKUP_DIR` defaults to `<data directory>/backups`, `LOOP_NOW_BACKUP_KEEP` defaults to 7); `loop-server backup <dir>` makes a manual backup at any time. The baseline is SQLite migration version 1, and the old PG migrations are not translated; existing instances use the one-off `loop-server import-postgres` (the source database must be at version 34; verified with a real backup on an isolated stack, with 87 tables and 134,038 rows checked column by column and found identical), and the `internal/server/pgimport` subtree keeps pgx and the PG migrations for the import only, to be deleted as a whole once the user has finished switching over. The health endpoint drops the postgres and redis fields and instead reports the database status and a WAL size warning. The change in credential exposure (processes of the same user can read the database file directly) is known to the user and accepted. The server cannot be compiled on Windows yet (the Lark sidecar and others use unix calls); that is a separate line of work. Stress testing: under concurrent writes, 12,000 random cancellations and 300 rounds of random SIGKILL, no acknowledged commit was lost.

- Windows server (2026-11-05, PR #33; only the server layer, with the desktop shell and the release pipeline done separately): `GOOS=windows go build ./...` and `go vet ./...` pass; CI gained a `server-windows` job (windows-latest: vet, build, all Go tests; autocrlf is turned off before checkout, and golden files are compared as LF) and the Windows cross-vet on Linux was extended to the whole repository; all six checks are green. Design decisions:
  - Process groups: the new package `internal/procgroup` unifies two implementations. On Unix it is Setpgid plus kill(-pid); on Windows it is a Job Object (CreateJobObject + JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, AssignProcessToJobObject after Start, and TerminateJobObject to terminate the whole group; whether the group is alive is not judged by ActiveProcesses (after the group leader exits and until its process object is destroyed it is still counted, which once led to a wrong "group not finished" verdict on CI) but by enumerating the PIDs in the Job and checking the exit code of each; when the server exits or crashes, the handle closes and the whole group ends), and child processes additionally get CREATE_NEW_PROCESS_GROUP and CREATE_NO_WINDOW. Windows has no SIGTERM that can be delivered: Terminate on a child process (Pi and others) is the same as Kill, and a graceful stop relies on closing their stdin first; the server's own graceful exit uses `LOOP_NOW_STOP_ON_STDIN_CLOSE=1` (off by default): the desktop shell launches `loop-server.exe` with it and closes stdin when it wants to stop it, the server handles that as if it had received SIGTERM (it cancels ctx, and `Shutdown` completes within `LOOP_NOW_SHUTDOWN_TIMEOUT`), and after the timeout the shell falls back to `taskkill /T /F`; macOS still uses SIGTERM. There is a very small window between CreateProcess and Assign; processes left over from a previous instance can only be ended by PID, and their descendants have already ended when the old Job closed. All the Setpgid/syscall.Kill call sites in executor, pluginhost, cliauth, modelauth, cliverify, tasks, folders, larksidecar and cliimport now use it.
  - Locks: the primitive behind the instance lock and the work root lock is extracted into `internal/filelock` (flock on Unix; on Windows, LockFileEx locking the first byte), and cliverify's lease lock uses it as well.
  - Permissions and symbolic links: the new package `internal/privatefs`. On Windows, 0700/0600 is a protected DACL that contains a single ACE, for the current user (inheritable on directories, so once the work root is made private, files newly created under it are private automatically); the checks go through GetNamedSecurityInfo/GetSecurityInfo and allow only allow-ACEs for the current user, SYSTEM and BUILTIN\Administrators (the latter two correspond to root on Unix, which bypasses the permission bits anyway; user directories naturally carry these two inherited ACEs; this is the same criterion OpenSSH for Windows uses), and "owned by the current user" compares the owner SID; opens with O_NOFOLLOW go through os.Root on Windows (O_NOFOLLOW_ANY, which rejects any symbolic link or junction in the path), and the executable-bit check goes by file extension. larksidecar's opening of its inputs, cliimport's reading of sources and executor's home reclaim each have an os.Root version (Windows has no openat).
  - Default directories: the data directory is `%LOCALAPPDATA%\Loop Now\data` (the context directory is in the same place) and the work root is `%ProgramData%\loop-now`. The work root must be outside the user profile directory (Pi loads AGENTS.md/CLAUDE.md from every ancestor directory going upward, and LOCALAPPDATA is inside the user directory); ProgramData is the counterpart of /var/lib and /Users/Shared, ordinary users can create directories in it, and the startup check makes it accessible to the current user only.
  - Child process environment: `internal/execenv` provides the system directories (System32, Windows, Wbem, WindowsPowerShell) and the basic variables that Windows child processes need (SYSTEMROOT, COMSPEC, PATHEXT, plus USERPROFILE/APPDATA/LOCALAPPDATA/TEMP set according to the separate HOME); the execution PATH, the Pi environment, the auth helper, the plugin host, CLI verification and the database CLIs all carry them. Paths always go through filepath, and the PATH separator is os.PathListSeparator.
  - Starting Pi: when PiBin is a .js file (the bundled cli.js) it is run by the bundled node (`preflight.PiCommand`), which on Unix has the same effect as the shebang; on Windows, pi.pid records the creation time from GetProcessTimes to guard against PID reuse, and old files without that record are no longer compared using ps.
  - Release layout (the Windows package; `scripts/release/build.sh` still handles only darwin/linux, and someone else will add the rest): `loop-server.exe`, `loopctl.exe`, `loopctl-dist/`, `runtime/node/node.exe` (the official zip unpacked, with its top-level directory removed), `runtime/pi/node_modules/@earendil-works/pi-coding-agent/dist/bundle/cli.js`, `plugins/host/main.js`, `plugins/official/`. The server looks for these relative paths from the directory that contains loop-server.exe (`config.BundledNode` is `runtime/node/node.exe` on Windows; the rest is the same as on Unix). How to run it: unpack it and run `loop-server.exe` directly (or let the desktop shell launch it); the data directory and the work root take the default directories above, and environment variables can still override them.
  - Not verified and not available: CI runs only the Go tests, and no smoke test with a real Pi has been done on a Windows runner; the channels that pass private fds through ExtraFiles (the model OAuth login helper, the Google CLI helper, the in-task OAuth refresh bridge, and the import of MySQL login files) are not supported by os/exec on Windows and fail with an error as soon as they start, and they have to be changed to named pipes before they can be used; running as a Lark user depends on macOS sandbox-exec and is not available on Windows; on Windows, cliimport's source identity has only mode/size/mtime; the Pi runtime recovery proof is implemented only for darwin, and Windows, like Linux, is treated as unconfirmed. Tests that depend on Unix permission bits, FIFOs, /bin/sh or process group queries run only on unix, by build tag.

- Context and Agent folders are deployed locally: an Agent in a project gets its own context and that project's context, a platform Agent gets its own context and the global context, and an in-task Agent's own part is reclaimed along with the task. The project/global context is an ordinary folder, by default under `~/.loop_now` (in the home directory of the user the service runs as); it can be changed with environment variables, and both people and Agents can modify it. A regular Agent has only one folder, which is its working directory and also its own context: on the page you can upload, browse, edit and delete, and you can do a one-off pull from Git (optionally pulling only a specified branch); there are no folder sources and no syncing any more; when a task starts the whole folder is copied (an APFS clone) and it is reclaimed when the task ends, and an Agent in a task fetches/pulls the branches it needs by itself before starting work. Writing is left to the Agent's own judgment (decisions, corrections, facts that others need, handoffs, and when submitting a node result); the rules are put into the built-in Skill, and process logs and information that can be looked up are not written. The entry point of each layer is the `AGENTS.md` at the root of the folder; every time Pi starts, the entry points of the two layers visible to that Agent are put into the system prompt (its own is read by Pi from the working directory, and the project or global one is added by the platform), and the other files are read on demand. A change to an entry point is not reloaded immediately; it takes effect after Pi restarts naturally (idle reclaim or a configuration change). File organization (one file per topic; the entry point serves as the table of contents and records the most important conclusions; whoever changes something keeps the entry point in sync; whatever is out of date is changed or deleted right away) is managed by the Agent itself, and the platform does not truncate the entry point. File operations on the page are placed in three places: Agent config, project settings and global settings; when a person and an Agent make changes at the same time, the later write wins; the task copy and the session fork happen at the same moment (after the base Agent's current turn ends); pulling from Git pulls only the specified branch and keeps that branch's full history; deleting an Agent keeps its folder and session (the current behavior), and deleting a project keeps its context folder; the old “文件夹来源” (folder sources) is retired, but its data is kept. - The second version of the plugin system (spec `plugins/SPEC.md`, protocol `api/plugin-host-protocol.md`) has been implemented, replacing and dismantling the first version (the old tables, old host, old pages and old Node code are all deleted, and data is not migrated). A plugin is a directory; in `package.json` the `pi` section declares the Agent side (extensions, Skills) following the Pi standard, and the `loopNow` section declares the platform side (events, permissions, configuration Schema, accounts, MCP servers, CLIs, action buttons, HTTP endpoints, schedules, channels); the manifest has the final say, and code that goes beyond what is declared fails to load. The Agent side is attached to that Agent's Pi as Pi extensions when the plugin is granted (`-e`, `--skill`, the merged `mcp.json` plus `-e builtin:mcp`, PATH, environment variables); the platform side is loaded into one shared, long-running Node host (stdio JSON lines protocol; it stops after 3 crashes within 5 minutes, can be restarted manually, and can be disabled globally with one click). Events come in four kinds, intercept/modify/claim/observe; the observe kind is written by a trigger inside the business transaction and delivered at least once; the platform side calls the console API with an `lnp_` token within the declared scopes. The host provides persistent state, secrets (stored in the database in plain text, never echoed back, injected only into the plugin they belong to) and generation of the configuration form; the SDK `@loop-now/plugin-sdk` provides the types and a delivery library with retries (delivery records are displayed under an agreed key). Install sources: official (released with the platform), local directory, git, npm, the market index repository; a preview first shows the content of both sides, the events and the permissions, and non-official sources need confirmation; after a project enables a plugin, it is granted per Agent. Official plugins: `webhook` (a signed POST as soon as the inbox has a new message, replacing external polling), `hello` (one minimal example on each side), `playwright` (a dedicated Chromium, a separate configuration directory per Agent, the browser prepared once). A Pi extension's confirm/select/input is turned into a question to you in ordinary conversations, and is handled as cancelled in task turns (the user's decision: when a task needs a person to decide, it asks through the inbox). A plugin can manage external identities on their behalf (spec §12): in the manifest the channel declares `manageIdentities` and the permission `identities.manage`; the managing plugin is chosen on the external identities page (console only); messages and questions sent to a managed identity are delivered as `identity.inbound` only to the managing plugin; the plugin uses `asIdentityId` to reply or answer as that identity, with the same effect as the identity replying in person, and the audit records that it was done on the identity's behalf; the official `webhook` is the reference implementation (the push carries the options and a callback URL, and after verifying the signature it answers for the identity), and channels such as Feishu are for plugin authors to implement along the same lines.

## Local development and running

Dependencies: Go 1.27, Pi 1.4.0 by default, Node 24.21.0; PostgreSQL and Redis are not needed, and the database is SQLite in the data directory (default `~/.loop_now`, on Windows `%LOCALAPPDATA%\Loop Now\data`, changed with `LOOP_NOW_DATA_DIR`; the database is created automatically on first start). The full run parameters and their defaults are in `internal/server/config/`; for the frontend environment configuration see `web/.env.example`.

The server and loopctl must be the same version; in an environment with Node and Pi installed:

```sh
go build -o bin/loop-server ./cmd/loop-server
version="$(bin/loop-server version)"
go run ./cmd/loopctl-dist -version "$version" -out "$PWD/.local-build/loopctl-dist"
LOOP_NOW_LOOPCTL_DIST_DIR="$PWD/.local-build/loopctl-dist" bin/loop-server
```

Startup runs any missing migrations and restores the platform state; only one instance runs on the same data directory at a time (instance lock file). When updating an existing local service, keep using the original data directory and work root; to migrate from the PG version use `loop-server import-postgres` (the quick start in docs has the steps). Running as a Lark user additionally needs the reviewed authsidecar release package, configured through `LOOP_NOW_LARK_USER_BUNDLE_DIR`; the original bot uses the official CLI package.

```sh
cd web
./bin/npm24 ci
./bin/npm24 run dev
```

Choose the necessary checks according to the change: backend `go test ./cmd/... ./internal/... ./api/...`; Web `./bin/npm24 run typecheck`, `run api:check`, `run lint`, `test`, `run build`. Run `run api:gen` only when the API changes, and do not edit the generated types by hand.

GitHub Actions (`.github/workflows/ci.yml`) runs the required checks on pushes to main and on PRs: Go vet (including a windows cross vet of the whole repository) and all Go tests (no external services needed; the data layer stress test is a separate step), the server's vet / build / tests on a Windows runner (`server-windows`), the Web typecheck / api:check / lint / test / build, and the plugin workspace's build, tests and official plugin validation; there is also a non-required `importer (postgres)` job that brings a PG service and runs only the importer tests, to be deleted together with the importer; Node is pinned to 24.21.0 to satisfy web's engines constraint. Tests that depend on the local Pi, native helpers or macOS-only capabilities are skipped when the prerequisites are missing, which does not count as passing.

Backend tests need no external services, and each test uses its own temporary data directory; only the importer tests use `LOOP_NOW_TEST_DATABASE_URL` to point to a test database, and a skip for lack of configuration does not equal a pass. Browser and native CLI tests need their own fixtures (the integration tests' newWorld pins Pi 1.1.0, so the whole batch is skipped when this machine has 1.4.0; to be changed); temporary artifacts stay in `.local-build/`, and credentials and runtime data do not go into Git.
